# Radar reliability acceptance

1. Pin main SHA, exact PR head, latest production run, actual committed data revision. Read [project rules](../../../AGENTS.md), [data contract](../../../docs/model-data-contract.md), and [retrospective](../../../docs/reliability-retrospective-2026-11-28.md).
2. Execute `python scripts/report_acceptance.py --json` on the pinned checkout or read the exact corresponding `system-audit.json` gates. Always report same-stage event recall separately from fixed original-article recall and independent fact accuracy. For an already accepted event, use its evidence IDs and observed date; do not reopen it because the original URL fails. If actual stage gate regresses, inspect per-event row and evidence first. Never alter fixed truth to gain a hit or feed benchmarks into collection.
3. Reproduce the actual failing layer: runner transport (HTTP code, elapsed wall time, effective URL, retry state), content/identity/date/stage extraction, transaction/persistence, or Pages publication. Human browser success is not runner success. Compare current valid alternatives and unique verified contribution; respect robots, backoff, access policies. Prefer existing AIHOT/AIPick discovery and exact independent publisher proof. Do not infer cause from 403/404 alone. Hard budget is a wall-clock cap, not a socket timeout; demonstrate termination against a slow local fixture and honest retained-state behavior.
4. Before coding, check existing PRs/automations, shared touched paths, all callers, test contracts, and the smallest viable change. Avoid overlapping changes and repeated shared-document appends; keep feature notes in separate files. Record a regression test that fails on the actual defect. For workflow changes execute the exact production entrypoint in PR CI and preserve all former gate semantics; for optimization use the original implementation as an equivalence oracle rather than a retyped approximation.
5. Pre-merge: exact head full CI, Chromium and WebKit. Compare current main changes; on conflict merge main on the isolated branch, preserve both edits and rerun exact-revision checks. Do not force main or merge while an active production transaction could lose its commit. Post-merge: actual collection, data commit, live marker and deployment; distinguish push smoke from scheduled mixed-scope and warm cache tests.
6. Report a compact gate matrix, evidence paths/run IDs, scope-comparable timing (including outliers), and actual remaining blockers. Do not equate a single favorable run, cached evidence, or simulated tests with a production SLA or fresh independent factual review. A failed candidate is not a production rollback. Stop repeating accepted work; keep separate non-blocking transport health visible. Do not change the Mac schedule or invent completion.
